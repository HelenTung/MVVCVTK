## 0. 任务分类与开工

工程开工按以下顺序执行。工作树选择与 baseline 授权按 md/development/core/GIT_WORKFLOW.core.md 第 2.1 节执行。

**第一步：完成开工闸门。** 规范读取、补读、加载确认与后续动作的先后顺序，统一按根 AGENTS.md 的“开工闸门”执行。

**第二步：核对现状。** 必须先看清现状：Git 仓库使用以下四项检查，这四项固定只读检查可以直接执行，其权限由本节定义；其他资产按实际情况核对，不虚构 Git 仓库。只在已指定工作树执行这四项，不因此加载 Git 专项；超出四项的 Git 操作，以及分支、工作树、baseline 或文档维护位置判断，先按根开工闸门读取该动作对应的 Git 单元。

```text
git rev-parse --show-toplevel
git status --short --branch
git diff --stat
git diff --cached --stat
```

**第三步：读取目标材料。** 读与目标直接相关的既有实现、文档、构建或依赖配置及验证入口。新增类型、函数、模块或文档前，先搜索有没有同职责的已有实现。

复杂任务在动手前写一段简短的范围说明，放在会话里即可：

- 要解决什么问题，完成后能观察到什么结果；

- 改哪些模块，明确不做什么；

- 怎么验证。

需要最新远端状态、分支或工作树操作时，按 md/development/core/GIT_WORKFLOW.core.md 执行。

- **适用范围**：所有任务都按本文件第 1 节的 Loop 工作方式执行，并按以下三类处理。工作树选择及 baseline 写入例外见 md/development/core/GIT_WORKFLOW.core.md 第 2.1 节。

<a id="read-only-task"></a>

- **只读任务**：按源文件是否修改划分；对源文件只读取、检索、核对。证据文件的生成不改变该分类，但证据输出目录与可写范围必须在派发中单独授权，不因源文件只读而默认获准写入任意位置；位置与保留要求按 md/development/core/GIT_WORKFLOW.core.md 第 2.3 节及项目配置执行。不新建派生工作树，不建 任务进度文件，不写归纳笔记。报告按本文件第 1 节的简单任务方式和 相应收件人的报告要求写：执行者给协调者按 md/development/core/COLLABORATION.core.md 第 13.3 节，子代理给执行者按其第 13.4 节，协调者给用户按本文件第 14.2 节；派发中给了编号验收项的，逐项标明状态。

- **只写文档的任务**：只修改文档（规范、说明等，格式范围由项目配置或当前资产确定），或只改代码、构建配置或脚本中的注释，且所有非注释内容保持不变（下文称“纯注释改动”）。不运行产品构建与测试，不新建派生工作树，不建 任务进度文件，不写归纳笔记；文档直接在用户或协调者指定的工作树中修改，项目规范和说明默认在主工作树维护，按 md/development/core/GIT_WORKFLOW.core.md 第 7 节执行；纯注释改动直接在所在工作树修改。验证按 md/development/core/ENGINEERING.core.md 第 11 节及项目风险细则的适用等级执行；现行项目规范的静态检查、独立复核与行为场景验证按该文件第 11.1 节执行，不因文档分类免除。提交仍按 md/development/core/GIT_WORKFLOW.core.md 第 0 节的 Git 权限执行。报告要求同只读任务。

- **开发和实验任务**：修改代码、构建配置或脚本的非注释内容（纯注释改动按本节“只写文档的任务”处理），或者需要产品的 configure、构建、测试或复现（规范资产的验证按本节“只写文档的任务”处理）。工作树按 md/development/core/GIT_WORKFLOW.core.md 第 2.1 节选择，任务进度文件 按本文件第 2 节建立和维护；目标收尾按本文件第 3 节写归纳笔记，按 md/development/core/GIT_WORKFLOW.core.md 第 6 节清理。

- **baseline 上的发行与合并**：适用范围见 md/development/core/GIT_WORKFLOW.core.md 第 2.1 节。不建立 任务进度文件，收尾时也不生成；恢复信息只写在会话报告中，包括当前提交、改动、最近一次验证和下一步，收尾只按本文件第 3 节写归纳笔记。

- **记录与授权**：记录方式不改变文档修改位置和操作权限，仍须遵守本文件第 7 节和 md/development/core/GIT_WORKFLOW.core.md 的授权边界。

### 0.1. 会话启动自检

完成根 AGENTS.md 的“开工闸门”后，会话开始工程任务前做一次启动自检：确认已读取本目标适用的任务记录，明确所在角色，核对自身实际提供方、模型、思考强度、权限模式与项目规定一致，必需配置已经在位。是否建立任务进度文件只按第 0 节分类，不因自检改变条件。项目没有指定的字段不自行加要求；必要任务状态不存在时先向直接上级取得必要上下文，不凭会话记忆补造。

实际设置以运行时可信元数据或派发方已经核实的实际快照为依据，不能拿创建请求参数代替实际结果。自身快照由派出自己的上级核实并提供，不把它变成每次都要反问上级的固定流程，也不为自检越权查询其他会话。发现不一致或无法核实，先向直接上级报告，暂停依赖正确配置的工程动作；纠正并重新核实后再开工。该自检不改变授权门禁。

执行者与子代理回执第一行写“启动自检：通过 / 未通过 / 未核实”，并简述角色、实际模型/思考强度/模式、必需配置核验结果与证据来源。未验证的配置如实标为未核实，不能把文件声明当成运行态生效。

## 1. 工作方式

Loop 是明确目标、执行、核对、处理缺口和收尾的工作方式，不等于建立记录文件。简单任务在会话中说明目标、执行结果、核对结论及剩余缺口即可，不强制五段模板或工具操作流水；子代理只读与提取任务的回执内容以 md/development/core/COLLABORATION.core.md 第 13.4 节“结构化输出与改动回执”为准。

完成阶段目标、出现阻塞、准备交接或收到改变当前安排的派发时，结束一轮，按适用的记录方式更新当前状态。

实现完成待集成、阶段结果和未终止的阻塞，只更新当前记录（任务进度文件 或会话报告），不写归纳笔记。归纳笔记的时机见本文件第 3 节。

执行者根据当前缺口调查、修改或验证。发现问题就修正原因，回到出问题的环节，补齐受影响的证据；已有的有效证据直接复用，没有新依据时不重复同一个失败动作。满足验收范围后交回协调者；缺少必要输入、需要新增授权或返工轮次用完时，报告当前结果和具体阻塞。验证范围和证据复用见 md/development/core/TESTING.core.md 第 3.2 节、md/development/core/TESTING.core.md 第 19.2 节，职责与报告见 md/development/core/COLLABORATION.core.md 第 13.3 节。

形成可以独立审查的改动切片后，按 Git 权限提交；未完成的验证如实写明。提交规定见 md/development/core/GIT_WORKFLOW.core.md 第 3 节。

## 2. 任务进度文件规则

- 开发和实验任务按开头的分类确定记录方式。需要建立任务进度文件的目标只建一份。

- **根任务**：协调者派发的根任务按开头的分类建立记录，文件放在根任务派生树的任务目录根部。协调者直接派发的验证任务也是根任务，有自己的派生树和 任务进度文件。

- **派生起点**：从协调者指定的 baseline 创建；未指定时使用默认 baseline，含义见 md/development/core/GIT_WORKFLOW.core.md 第 1.3 节。起点提交、创建命令与记录、baseline 写入限制的适用范围见 md/development/core/GIT_WORKFLOW.core.md 第 2.1 节。

- **子树**：执行者为同一目标再派生的子树不建自己的 任务进度文件，包括验证、独立复核、并行开发和子任务集成树；只把证据交给根任务负责人汇总。

- **负责人**：一个目标只派给一个执行者时，它就是根任务的执行者；拆给多个执行者时，协调者指定唯一的根任务和负责人。

- **写入者**：任务进度文件由协调者维护，协调者是唯一写入者，只记入协调者层级的任务。执行者不直接写它，将所接执行任务的进展与证据位置汇报协调者；执行者给其下级的任务记录按第 2.1 节执行。归纳笔记仍由根任务执行者准备。

- 文件只包含两节，开头为 **当前状态**（在运行、下一步、阻塞），其后为 **证据索引**。“当前状态”每次更新时覆盖重写，不追加历史，不保留被替代的计划和更正记录。

- 每条验收标准编号（如 验收1、验收2）。目标、编号和内容只由协调者在派发中确定，执行者按派发内容执行并汇报，不直接改写记录。

- 文件中的两个节标题一律保留，暂时没有内容就留空；这一条不受本文件第 7.1 节“不适用的章节直接省略”的约束。

- 执行者每轮先读本目标的当前记录，在本文件第 1 节规定的时机由写入者更新。任务进度文件只保存当前状态和恢复所需信息，不逐次记录工具操作；使用 Markdown，不新增 JSON 文件。“证据索引”每完成一个任务只增加一行，内容为任务号、结论、证据位置；同一任务的有效结论或证据变化时覆盖原行，不另加重复行或更正记录。

- 最小恢复信息写在“当前状态”：当前分支和提交、未提交改动的归属、最近一次有效验证及必要的启动、环境恢复或复现命令；已完成任务的详细证据通过“证据索引”的位置读取，需要脚本时沿用现有 脚本工具。

- 已有任务文档的收尾处理见本文件第 3 节。

### 2.1. 派发前的 DAG 与批次记录（唯一定义）

任务拆分与 DAG 的决定权按 md/development/core/COLLABORATION.core.md 第 13.1 节执行。协调者与执行者在派发任何下级会话前，都必须先把子任务、依赖关系、就绪批次与并发安排形成可核对记录。未写好 DAG 记录不得派发，适用于协调者与执行者。是否建立任务进度文件只按第 0 节分类，不能因派发改变分类条件；各层的记录载体按下段执行。

协调者层级的 DAG：需要任务进度文件时记入该文件，不建该文件时记在会话或指定工作记录中，不另建任务进度文件。执行者给其下级的 DAG：由执行者自己在给协调者的汇报或自己的工作记录中写明后即可派发，不等待协调者记入；协调者在验收时审查。任务进度文件的维护者只按第 2 节“写入者”执行。所有层级每派发一个任务都必须给出任务编号和指定执行者或子代理，编号用中文与数字（如“任务3”“执行者1”“子代理1-2”），不用英文字母；DAG记录写明“任务编号—指定执行者或子代理编号—负责内容”。

各层按上述载体记录当前 DAG 与批次；任务进度文件按第 2 节覆盖更新“当前状态”，完成任务按该节写入“证据索引”。至少记录子任务、负责角色、源文件唯一写入范围与单独授权的证据输出范围、上游依赖、同批就绪任务、计划与实际并发数、未并行原因、当前状态、配置核实和归档结果。发现记录遗漏时如实上报，不能把补写内容称为事前计划。

只读单任务的填写示例见项目配置“协作示例材料”，由协调者按需读取。

需要任务进度文件时，位置沿用本节的根任务任务目录。尚无任务树时由协调者在项目或平台规定的临时位置建立同一份记录，派发写清位置；树就绪后由协调者转到任务目录根部，不在 baseline 留进行中的记录，不另建第二份当前记录。用户指定位置时采用指定位置。

- **全局规划与任务 DAG**：开工时把目标拆成若干执行任务，画出任务依赖有向无环图（DAG，Directed Acyclic Graph）。前置条件已满足、剩余入度为 0 的任务视为就绪任务，在并发上限内同批并行派出；任一任务完成、失败或被裁决改变时，重新评估 DAG，立即派出新就绪任务，不等整批结束。

依赖同时包括逻辑先后、md/development/core/COLLABORATION.core.md 第 13.2 节“写入隔离”条规定的重叠写入或单一 owner 契约、写入同一 baseline（如合并、转移记录）、共用同一构建目录，以及下游方向取决于上游结论（如先调研再定方案）。是否存在实际写入冲突、不同物理树的开发并行和 baseline 合并串行，统一按 md/development/core/COLLABORATION.core.md 第 13.2 节“写入隔离”判断。有这些依赖的任务串行执行或合并为一个任务；baseline 的写入顺序与占用检查按本文件第 5 节执行，只读检查可以并行。

同时运行的执行者不超过项目配置的执行并发上限；执行者派子代理的上限按 md/development/core/COLLABORATION.core.md 第 13.4 节执行。就绪任务超出适用上限时按优先级排队。资源占用重的任务并行前，先核对机器负载，必要时降低并行数并说明理由。新开还是续用执行者，仍按md/development/core/COLLABORATION.core.md 第 13.2 节“按方向新开执行者”条判断。任务进度文件 的份数、位置和写入者见本文件第 2 节。

派发后由执行者及时汇报实际会话和配置核实结果；任务完成、失败或依赖变化时，各层更新自己的当前记录，任务进度文件仍只由协调者按第 2 节更新。由 md/development/core/COLLABORATION.core.md 第 13.1 节确定的上级重新评估就绪任务，再派发。协调者验收时对照实际派发与结果，检查依赖、批次、并发、配置核实和归档是否相符；缺记录或矛盾须退回补查，发现遗漏如实报告偏离，不能补造事前计划。

派发记录的已填表单见项目配置“协作示例材料”，不另定义义务。

## 3. 存放与写回

收尾写回上一级的 Markdown 仅包括必要证据、归纳笔记、协调者维护的对应任务进度文件；其余过程文件和临时输出不随之写回，按 md/development/core/GIT_WORKFLOW.core.md 第 2.3、6.6 节及既有证据保留要求处理。此范围不扩大删除权限。任务进度文件由协调者维护和转移，执行者只准备并交回其他收尾资料。

- 需要任务目录时，按本文件第 7 节组织。协调者在派发时明确本目标的根 baseline、任务目录和上级任务；baseline 和根 baseline 的含义见 md/development/core/GIT_WORKFLOW.core.md 第 1.3 节。

- 新建的 任务进度文件 和 收尾笔记文件 是本地记录，不提交到 Git，不强制添加被忽略的文件。已有任务文档按本节的收尾留存规则处理；权限见 md/development/core/GIT_WORKFLOW.core.md 第 0 节。

- **归纳笔记的计数**：按协调者声明的目标计数，一个目标在根 baseline 留一份。子树结束时只交证据，不另写笔记；协调者不自己写笔记。

- **收尾时机**：全部结果合回根 baseline，或目标被明确终止时，目标收尾。只在这时写归纳笔记，在交回协调者前写好；验收需要补证据时更新同一份笔记。

- **整理记录**：已建立任务进度文件的目标，由协调者按第 2 节覆盖更新“当前状态”并核对“证据索引”。删去可重建的过程流水，如逐条命令输出和换行对比。

- **收尾状态**：整理后的任务进度文件在“当前状态”中写明状态（“已结束”“已终止”或“可续接”）、最后的提交 SHA 和分支名。

- **逐级转移**：结果再合入上一级时，收尾记录按 md/development/core/GIT_WORKFLOW.core.md 第 6.2 节转移，直到主工作树；根 baseline 自身回收且没有接收树时的保留位置也按该节处理。

- **无源码变更或终止的目标**：无源码变更的独立验证以全部结果汇总完成作为目标收尾，不要求空 Git 合并。目标被明确终止时，写明未合入状态、已完成内容，以及未完成、未验证事项；不为留档合并未合入的结果。

- **进行中的记录**：根 baseline 不放进行中的过程文件；派生根任务的 任务进度文件 在整个目标收尾后才整理归档到根 baseline。

- **收尾留存**：新任务优先使用本文件规定的记录和既有测试记录，不另建过程文档。

- 已有过程文档按本节收尾写回范围核对，不因曾经存在而扩大转移清单。

- 已被 Git 跟踪的任务文档按正常 Git 流程处理，不自动取消跟踪。

- **笔记内容**：写清结论、关键改动和结果、限制，以及导致失败或阻塞的超时、关键差异和最小复现信息；关键数据写进笔记，证据只写索引（提交 SHA、复现命令、输入标识），不搬完整日志或过程流水。证据文件的存放和保留例外见 md/development/core/GIT_WORKFLOW.core.md 第 2.3 节。

## 4. 续接与优先级

本节的“目标”指协调者确定的总目标。总目标和验收标准不变、授权仍覆盖当前动作时，续用原执行者与按第 0 节适用的当前记录。同一总目标内从调研推进到获准实现等属于阶段推进；为该阶段补足实施许可不机械视为新方向，不能在许可取得前越界。改变总目标、验收标准或授权使原方向不再适用时才按新方向处理；跨写入范围前由协调者调整分工。已有派生工作树的继续沿用；从只读进入本就需要建树的阶段时，按 md/development/core/GIT_WORKFLOW.core.md 第 2.1 节创建派生树，由协调者按第 2 节建立所需任务进度文件。

只读和只写文档任务沿用原会话或指定工作记录续接；只有本就需要任务进度文件的目标才续用该文件。派发与有无 DAG 不改变第 0 节分类条件；开发和实验任务按以下规则处理：

- **继续**：总目标和验收标准不变时，在原派生工作树读当前记录接着做，或按本节的历史续接规则从历史 任务进度文件 接着做；例如会话中断换执行者、退回重改。协调者在派发中指明记录位置。

- **从历史记录接着做**：协调者在派发中指定起点是历史记录的提交还是当前 baseline。执行前确认选定提交仍可读取，再按 md/development/core/GIT_WORKFLOW.core.md 第 2.1 节创建派生树；从历史提交起步时使用该提交 SHA，并记明原因。

- **记录复制**：由协调者把历史任务进度文件 复制进新根任务派生树的任务目录，状态改为“进行中”，接着做。续接期间，baseline 中的历史副本保留不动。

- **续接时调整目标**：用户明确要求在原树续做并调整目标，或指定历史任务续做时调整目标，协调者在派发中写明调整后的目标与验收标准及调整原因；由本文件第 2 节规定的写入者覆盖更新“当前状态”。原树续做沿用原工作树、原分支和原文件。

- **新任务**：总目标或验收标准改变时，开新派生工作树和新的 任务进度文件，需要的旧结论由协调者写进派发内容；上一条规定的续接例外除外。

- **原工作树已删除**：有历史 任务进度文件 时按本节的历史续接规则处理。没有历史文件而同一未结束任务的原分支仍在时，按 md/development/core/GIT_WORKFLOW.core.md 第 2.1 节重新挂载原分支，由协调者根据执行者交回的归纳笔记、提交记录和派发内容重建记录；原分支也不存在时，按新任务处理。

- **续接收尾**：协调者更新根 baseline 同一目标目录中的任务进度文件，根任务执行者准备收尾笔记；记录都保留当前有效版本。

- 派生工作树按 md/development/core/GIT_WORKFLOW.core.md 第 2.1 节、md/development/core/GIT_WORKFLOW.core.md 第 6 节只服务一个用途并在用途结束后清理，不把旧 任务进度文件 留给下个任务。

- baseline 上的发行与合并按开头的分类用会话报告续接，收尾记录按本文件第 3 节留存。

协调者最新的派发内容优先于记录中的“下一步”，执行者按新派发推进并汇报，协调者更新适用的任务进度文件；不建文件的任务由执行者更新会话回执或指定工作记录。方向决策与派发职责见 md/development/core/COLLABORATION.core.md 第 13.2 节；写回按本文件第 3 节执行，提交按 md/development/core/GIT_WORKFLOW.core.md 第 3 节执行。

### 14.1. 裁决、通知与独立授权

L0–L3 定义谁来决定，D0、R1–R3 定义变更风险与验证要求，两套分级是不同概念。变更风险只引用 md/development/core/ENGINEERING.core.md 第 11 节及项目细则，不在本节复述。执行者必须在派发范围与风险等级内执行，不能把低风险或已获执行许可当作扩大方向、范围或独立授权的依据。

- L0：不改动目标资产的取证与核对，不改变已定目标、方向、范围、验收标准或授权；涉及这些取舍时按实际决定类型提高级别，不能因动作只读而一律标 L0。
- L1：在派发范围、方向、变更风险等级、预算与已有授权内，决定低风险改动或执行细节，不改变上级已经批准的事项；变更风险的最低决定级仍按下表核对。
- L2：任务范围内需要协调者决定的方向或取舍，由协调者自主决定后告知用户；下级先暂停受影响部分并逐级上报，不自行作出 L2 决定。
- L3：需要用户裁决或新授权的事项，由协调者先交用户，给事实、影响、可选方案与建议，未获决定前只暂停依赖部分。已有明确且仍有效的用户指令覆盖该事项时直接执行，不重复确认。

**决定权限阶梯（唯一定义）**：子代理只能自行决定 L0；执行者最多自行决定 L1；协调者可以决定 L2 并告知用户；L3 必须由协调者上报用户取得决定或授权。超过本层权限时，子代理报执行者、执行者报协调者，不越级自行决定；角色可执行动作与写入禁区仍按 md/development/core/COLLABORATION.core.md 第 13 节执行。

**已批准决定的落实（唯一定义）**：决定权限与下表约束首次或新增决定，不要求对已作出的有效决定重复报批。已批准的 R2/R3 任务，在批准的范围、方向、风险等级、预算与授权内直接落实；实现细节选择仍不得超过本层决定权限。执行者可以落实上级已批准的方案，子代理可以按执行者明确改动说明落实获准写入，这不等于下级自行作出该风险等级的批准决定，也不改变实际风险与验证义务。发现需要超出已批准等级、超出既定方向、扩大范围或取得新授权时，立即停下受影响部分并逐级上报裁决，不自行升级后继续。

**变更风险到最低决定级的下限表（唯一定义）**

| 变更风险等级（定义见 md/development/core/ENGINEERING.core.md 第 11 节） | 最低决定级 | 处理 |
| --- | --- | --- |
| D0、R1 | 至少 L1 | 首次或新增改动决定由有权限的角色在任务范围与已有授权内作出；不改动的取证与核对按 L0 判据处理。 |
| R2 | 至少 L2 | 首次或新增 R2 变更决定由协调者作出并告知用户；下级遇到未覆盖的新决定先停下上报，已批准部分按本节“已批准决定的落实”执行。 |
| R3 | 至少 L2 | 同 R2；仍按 R3 完成适用的完整验证与独立复核，不降低验证义务。 |

本表只规定最低决定级，不把两套分级等同；按决定类型可以提高。下文独立授权门禁中的事项始终须有用户决定或授权，与变更风险等级无关。

仍需用户授权的独立门禁有六类，不因 L0–L2 的自主决定或免确认模式而跳过：主干提交与合并；push、tag、release、创建 PR、删除远端分支；目录与工作树删除；SDK 边界变更；修改现行规范；在互不兼容的架构之间选择。目录与工作树删除需用户授权；满足 md/development/core/GIT_WORKFLOW.core.md 第 6 节删除条件的，视为已获默认授权。删除条件与执行分工只在该节定义；派发注明依据的条件条款与精确路径，不扩大删除范围。其他 Git 操作细节见 md/development/core/GIT_WORKFLOW.core.md 第 0、5 节，SDK 具体边界及落实见项目交付规范。

现行规范是正在作为会话工作规则生效的规范。现行项目规范集合由项目入口登记，并包含任何工作树本轮实际生效的其他项目规范，包括适用的局部 AGENTS.md；仓库内由项目维护的 core、平台和运行时适配文件属于该集合。修改现行规范必须先获用户明确批准，包括小改、单行修改与紧急修正，L0–L2 自主决定不涵盖此项；明确批准具体修改方案可作为落实该方案的指示，不扩展到方案之外。仓库外个人规则与平台自身规则另行核对其来源和可修改权限，仓库任务不默认授权修改它们，运行平台与工具硬性限制仍按 md/development/core/AGENTS.core.md 第 1.1 节执行。候选规范是用户指定用于研究、比较和修订，尚未替换成现行工作规则的材料；按用户指示修订候选不受这项现行规范门禁限制。读取候选作解释不会使其自动成为现行规范，Git 跟踪、忽略状态或文件名也不能代替该属性判断。

核心状态机变更按风险表定级。独立授权、任务既定范围和风险裁决分别核对，协调者自主决定不产生额外操作许可。

先完成必要调研再提交 L3 裁决或请求独立授权。事实问题中能自行取得的信息由协调者在动作边界内调研或派执行者调研；确实只能由用户提供的必要输入，调研后可由协调者向用户提问，在回复的“待办与风险”中标明“需要你提供”，说明缺什么、影响和下一步。这是取得事实输入，不是把决定交给用户；不虚构输入，只暂停依赖该输入的部分，继续其他可独立推进的工作。

执行者和子代理不直接向用户提问；分别按 md/development/core/COLLABORATION.core.md 第 13.3、13.4 节向上报告需要协调者裁决的事项。

### 14.2. 协调者给用户的回复模板

本模板只用于协调者回复用户；工程触发条件按 md/development/core/AGENTS.core.md 第 0 节执行。执行者向协调者、子代理向执行者的汇报分别按 md/development/core/COLLABORATION.core.md 第 13.3、13.4 节，不使用本模板。

**状态：已完成 / 进行中 / 受阻 / 待你决定**

**结论**

必填，用一段话简明说明现状及是否需要用户行动。

**处理方式**

进行中或受阻时必填；其他状态只要本轮有直接处理、派发或等待，也不得省略。第一项为“**由我直接处理：**”，在同一条中说明协调者直接处理的事；多件事用分号分隔。之后每个已派发执行者独立一项，标题为“**任务N — 执行者N（会话编号前几位，模型，思考强度）：**”，后接要做的事与当前状态，状态写在该项句末，如“进行中。”或“已完成。”。尚未派发的执行者也独立列出，在标题括号中注明“尚未派发”即为其状态，句末不另写状态；正文概述启动条件，不虚构会话编号或实际模型配置。不同执行者不合并成一段。只写协调者交给执行者的任务内容及当前状态，不写执行者内部如何拆分、如何分配或派了哪些下级。对用户不列子代理，子代理情况由执行者在向协调者的汇报中负责。正在等待时写在等谁、等什么及下一步；下一步放在本节内。

**完成情况**

本轮已形成任务交付结果或阶段成果时，列出解决了什么、做到哪一步；只作沟通、派发且尚未形成交付结果时可省略。

**主要变化**

本轮有用户能感受到的变化时逐条列出；没有变化时可省略。

**验证情况**

本轮有验证动作或需要交代的验证结论时列出，分开说明“已验证：检查内容与结果”和“未验证：未查项、原因及影响”；没有本轮验证结果信息时可省略。尚未验证的后续工作仍须列入“待办与风险”，不能随本节省略。

**自主决定**

本轮只要协调者自行作出了未经用户逐项确认的决定，就必须逐项写“加粗决定（实际 L 级）：理由”，级别按第 14.1 节判定，例如取证核对、选定任务记录位置或确定合并方向均按实际决定内容标注，不把协调者作出的所有决定都标为 L2；不能因决定小或已获总体任务授权而省略。没有这类决定时才可省略。落实已有明确决定而未产生新决定的，不虚构本轮自主决定。本栏目规定披露范围，不改变实际风险等级，也不扩大第 14.1 节的授权或裁决权限。

**需要你决定（L3）**

存在待用户裁决的事项时必填，写清背景、影响、可选方案和建议；没有待裁决事项时可省略。

**待办与风险**

只要存在未完成、未验证、阻塞、需要用户后续操作或已知风险中的任一项，就必须列出；只有这些情况确实都不存在时才可省略。确实只能由用户提供的必要输入，按第 14.1 节标明“需要你提供”，说明缺项、影响与后续动作。

本模板使用独立加粗栏目标签，不采用 Markdown `#` 标题语法；状态行与每个栏目标签单独成行。此呈现说明不改变指令优先级。若更高层指令禁止上述呈现形式，仅调整冲突的格式，仍须保留全部适用栏目的实质内容，并简述冲突及处理；不得因格式受限省略任务号、执行者、实际配置与状态、决定等级及理由、验证缺口和待办风险。结论为一段话。所有运行环境统一使用扁平版：栏目内只用单层项目符号，不使用嵌套子项或表格；每项只写一条，以加粗短标签及冒号开头，后接一句或几句完整说明。处理方式中执行者的任务与状态按本节专门要求写在同一条中。是否省略各节只按上述事实条件判断，不把“事项小”或“本轮暂不处理”当作没有内容。进度更新和完成回复都使用本模板，不另设“状态、结论、处理方式、下一步”的四项格式。使用平实、专业、整齐有条理的中文，不用英文缩写；角色编号写作“执行者1”，必要的产品名、文件名、代码标识符、命令、路径、模型名和错误码按 md/development/core/AGENTS.core.md 第 1.3 节原样保留。

协调者在本会话首次按本模板回复用户之前，必须读取[已填回复示例](../../agent-guides/协作记录与回复示例.md#coordinator-reply-example)；可复用本会话已读且未变化的该示例，示例与历史材料不定义当前义务、任务状态或额外授权。
