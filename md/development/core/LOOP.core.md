# 工作推进、任务记录与笔记

> 加载范围与角色身份见 md/development/core/AGENTS.core.md 第 0 节；文件路径以规范包根为基准。参数只承接目录、格式、命令、模型和预算等具体值；本文件不要求任何特定项目架构。

## 0. 任务分类与开工

工程开工按以下顺序执行。工作树选择与 baseline 授权按 md/development/core/GIT_WORKFLOW.core.md 第 2.1 节执行。

**第一步：读取适用规范与 Loop。** 必须先读取适用的 AGENTS.md，按 md/development/core/AGENTS.core.md 第 0 节加载本任务适用的主题规范，再读本文件；项目另有工作推进规范时一并阅读。为定位规范，可先只读查询当前路径、仓库根与规则文件是否存在；除此之外，完成本步后再核对现状和读取目标材料。

**第二步：核对现状。** 必须先看清现状：Git 仓库使用以下四项检查；其他资产按实际情况核对，不虚构 Git 仓库。

```text
git rev-parse --show-toplevel
git status --short --branch
git diff --stat
git diff --cached --stat
```

**第三步：读取目标材料。** 读与目标直接相关的既有实现、文档、构建或依赖配置及验证入口。新增类型、函数、模块或文档前，先搜索有没有同职责的已有实现。

复杂任务在动手前写一段简短的范围说明，放在会话里即可：

- 要解决什么问题，完成后能观察到什么结果；

- 改哪些模块，明确不做什么；

- 怎么验证。

需要最新远端状态、分支或工作树操作时，按 md/development/core/GIT_WORKFLOW.core.md 执行。

- **适用范围**：所有任务都按 md/development/core/LOOP.core.md 第 1 节的 Loop 工作方式执行，并按以下三类处理。工作树选择及 baseline 写入例外见 md/development/core/GIT_WORKFLOW.core.md 第 2.1 节。

- **只读任务**：只读取、检索、核对。不新建派生工作树，不建 任务进度文件，不写归纳笔记。报告按 md/development/core/LOOP.core.md 第 1 节的简单任务方式和 相应收件人的报告要求写：执行者给协调者按 md/development/core/COLLABORATION.core.md 第 13.3 节，子代理给执行者按其第 13.4 节，协调者给用户按 md/development/core/LOOP.core.md 第 14.2 节；派发中给了编号验收项的，逐项标明状态。

- **只写文档的任务**：只修改文档（规范、说明等，格式范围由项目配置或当前资产确定），或只改代码、构建配置或脚本中的注释，且所有非注释内容保持不变（下文称“纯注释改动”）。不构建、不运行测试，不新建派生工作树，不建 任务进度文件，不写归纳笔记；文档直接在用户或协调者指定的工作树中修改，项目规范和说明默认在主工作树维护，按 md/development/core/GIT_WORKFLOW.core.md 第 7 节执行；纯注释改动直接在所在工作树修改。验证按 md/development/core/ENGINEERING.core.md 第 11 节及项目风险细则 L0 执行，提交仍按 md/development/core/GIT_WORKFLOW.core.md 第 0 节的 Git 权限执行。报告要求同只读任务。

- **开发和实验任务**：修改代码、构建配置或脚本的非注释内容（纯注释改动按本节“只写文档的任务”处理），或者需要 configure、构建、运行测试或复现。工作树按 md/development/core/GIT_WORKFLOW.core.md 第 2.1 节选择，任务进度文件 按 md/development/core/LOOP.core.md 第 2 节建立和维护；目标收尾按 md/development/core/LOOP.core.md 第 3 节写归纳笔记，按 md/development/core/GIT_WORKFLOW.core.md 第 6 节清理。

- **baseline 上的发行与合并**：适用范围见 md/development/core/GIT_WORKFLOW.core.md 第 2.1 节。不建立 任务进度文件，收尾时也不生成；恢复信息只写在会话报告中，包括当前提交、改动、最近一次验证和下一步，收尾只按 md/development/core/LOOP.core.md 第 3 节写归纳笔记。

- **记录与授权**：记录方式不改变文档修改位置和操作权限，仍须遵守 md/development/core/LOOP.core.md 第 7 节和 md/development/core/GIT_WORKFLOW.core.md 的授权边界。

### 0.1. 会话启动自检

会话开始工程任务前做一次启动自检：确认已读取当前适用规范与本目标适用的任务记录，明确所在角色，核对自身实际提供方、模型、思考强度、权限模式与项目规定一致，必需配置已经在位。是否建立任务进度文件只按第 0 节分类，不因自检改变条件。项目没有指定的字段不自行加要求；必要任务状态不存在时先向直接上级取得必要上下文，不凭会话记忆补造。

实际设置以运行时可信元数据或派发方已经核实的实际快照为依据，不能拿创建请求参数代替实际结果。自身快照由派出自己的上级核实并提供，不把它变成每次都要反问上级的固定流程，也不为自检越权查询其他会话。发现不一致或无法核实，先向直接上级报告，暂停依赖正确配置的工程动作；纠正并重新核实后再开工。该自检不改变授权门禁。

执行者与子代理回执第一行写“启动自检：通过 / 未通过 / 未核实”，并简述角色、实际模型/思考强度/模式、必需配置核验结果与证据来源。未验证的配置如实标为未核实，不能把文件声明当成运行态生效。

## 1. 工作方式

Loop 是明确目标、执行、核对、处理缺口和收尾的工作方式，不等于建立记录文件。简单任务在会话中说明目标、执行结果、核对结论及剩余缺口即可，不强制五段模板或工具操作流水。

完成阶段目标、出现阻塞、准备交接或收到改变当前安排的派发时，结束一轮，按适用的记录方式更新当前状态。

实现完成待集成、阶段结果和未终止的阻塞，只更新当前记录（任务进度文件 或会话报告），不写归纳笔记。归纳笔记的时机见 md/development/core/LOOP.core.md 第 3 节。

执行者根据当前缺口调查、修改或验证。发现问题就修正原因，回到出问题的环节，补齐受影响的证据；已有的有效证据直接复用，没有新依据时不重复同一个失败动作。满足验收范围后交回协调者；缺少必要输入、需要新增授权或返工轮次用完时，报告当前结果和具体阻塞。验证范围和证据复用见 md/development/core/TESTING.core.md 第 3.2 节、md/development/core/TESTING.core.md 第 19.2 节，职责与报告见 md/development/core/COLLABORATION.core.md 第 13.3 节。

形成可以独立审查的改动切片后，按 Git 权限提交；未完成的验证如实写明。提交规定见 md/development/core/GIT_WORKFLOW.core.md 第 3 节。

## 2. 任务进度文件规则

- 开发和实验任务按开头的分类确定记录方式。需要建立任务进度文件的目标只建一份。

- **根任务**：协调者派发的根任务按开头的分类建立记录，文件放在根任务派生树的任务目录根部。协调者直接派发的验证任务也是根任务，有自己的派生树和 任务进度文件。

- **派生起点**：从协调者指定的 baseline 创建；未指定时使用默认 baseline，含义见 md/development/core/GIT_WORKFLOW.core.md 第 1.3 节。起点提交、创建命令与记录、baseline 写入限制的适用范围见 md/development/core/GIT_WORKFLOW.core.md 第 2.1 节。

- **子树**：执行者为同一目标再派生的子树不建自己的 任务进度文件，包括验证、独立复核、并行开发和子任务集成树；只把证据交给根任务负责人汇总。

- **负责人**：一个目标只派给一个执行者时，它就是根任务的执行者；拆给多个执行者时，协调者指定唯一的根任务和负责人。

- **写入者**：任务进度文件由协调者维护，协调者是唯一写入者；执行者不直接写它，把进展、证据位置与需记录的事项写进给协调者的汇报，由协调者记入。归纳笔记仍由根任务执行者准备。

- 文件包含五部分：**目标与验收标准**、**当前缺口**、**已完成与证据**、**下一步**、**阻塞与待裁决**。

- 每条验收标准编号（如 验收1、验收2）。目标、编号和内容只由协调者确定，执行者按派发内容执行并汇报，不直接改写记录；后四部分由协调者根据执行者汇报维护。

- 文件中的五部分标题一律保留，暂时没有内容就留空；这一条不受 md/development/core/LOOP.core.md 第 7.1 节“不适用的章节直接省略”的约束。

- 执行者每轮先读本目标的当前记录，在 md/development/core/LOOP.core.md 第 1 节规定的时机由写入者更新。任务进度文件 只保存当前状态和恢复所需信息，不逐次记录工具操作。“已完成与证据”按验收项编号记录状态（未实现、待验证、通过、失败、阻塞）、最近有效结果和证据位置（提交 SHA、复现命令、派生工作树的输出文件），使用 Markdown，不新增 JSON 文件。

- “已完成与证据”保留最小恢复信息：当前分支和提交、未提交改动的归属、最近一次有效验证、已经排除的方向及原因。必要的启动、环境恢复或复现命令写在该部分或“下一步”中；需要脚本时沿用现有 脚本工具。

- 已有任务文档的收尾处理见 md/development/core/LOOP.core.md 第 3 节。

### 2.1. 派发前的 DAG 与批次记录（唯一定义）

任务拆分与 DAG 的决定权按 md/development/core/COLLABORATION.core.md 第 13.1 节执行。协调者与执行者在派发任何下级会话前，都必须先把子任务、依赖关系、就绪批次与并发安排形成可核对记录。未写好 DAG 记录不得派发，适用于协调者与执行者。是否建立任务进度文件只按第 0 节分类，不能因派发改变分类条件：需要任务进度文件的，必须记入该文件，口头计划或单独 DAG 报告不能代替；不建该文件的任务，先在会话或指定工作记录中写明 DAG，不另建任务进度文件。

任务进度文件的维护者只按本节“写入者”执行。执行者派发自己的子代理前，先向协调者提交按 md/development/core/COLLABORATION.core.md 第 13.1 节已决定的子任务、依赖、批次与并发安排供记录，确认协调者已记入需要的任务进度文件后再派发；这不是请求协调者代为拆分，执行者不直接修改该文件。所有层级每派发一个任务都必须给出任务编号和指定执行者或子代理，编号用中文与数字（如“任务3”“执行者1”“子代理1-2”），不用英文字母；DAG记录写明“任务编号—指定执行者或子代理编号—负责内容”。

记录放在任务进度文件的“下一步”中；实际进展与证据位置由执行者汇报，协调者记入“已完成与证据”，阻塞和待裁决写相应部分。至少记录子任务、负责角色与唯一写入范围、上游依赖、同批就绪任务、计划与实际并发数、未并行原因、当前状态、配置核实和归档结果。事后补记必须标明，不能称为事前计划。

**只读单任务示例（不另定义义务）**：派发前在会话记“任务1—执行者1—只读统计；写入范围为空；无上游依赖；首批就绪；计划并发1；仅一项就绪任务，无并行分工；状态待派发”。派后在同条记录补实际并发、状态、配置核实及归档结果；编号和字段仍按本节前述要求执行。

需要任务进度文件时，位置沿用本节的根任务任务目录。尚无任务树时由协调者在项目或平台规定的临时位置建立同一份记录，派发写清位置；树就绪后由协调者转到任务目录根部，不在 baseline 留进行中的记录，不另建第二份当前记录。用户指定位置时采用指定位置。

- **全局规划与任务 DAG**：开工时把目标拆成若干执行任务，画出任务依赖有向无环图（DAG，Directed Acyclic Graph）。前置条件已满足、剩余入度为 0 的任务视为就绪任务，在并发上限内同批并行派出；任一任务完成、失败或被裁决改变时，重新评估 DAG，立即派出新就绪任务，不等整批结束。

依赖同时包括逻辑先后、md/development/core/COLLABORATION.core.md 第 13.2 节“写入隔离”条规定的重叠写入或单一 owner 契约、写入同一 baseline（如合并、转移记录）、共用同一构建目录，以及下游方向取决于上游结论（如先调研再定方案）。是否存在实际写入冲突、不同物理树的开发并行和 baseline 合并串行，统一按 md/development/core/COLLABORATION.core.md 第 13.2 节“写入隔离”判断。有这些依赖的任务串行执行或合并为一个任务；baseline 的写入顺序与占用检查按 md/development/core/LOOP.core.md 第 5 节执行，只读检查可以并行。

同时运行的执行者不超过项目配置的执行并发上限；执行者派子代理的上限按 md/development/core/COLLABORATION.core.md 第 13.4 节执行。就绪任务超出适用上限时按优先级排队。资源占用重的任务并行前，先核对机器负载，必要时降低并行数并说明理由。新开还是续用执行者，仍按md/development/core/COLLABORATION.core.md 第 13.2 节“按方向新开执行者”条判断。任务进度文件 的份数、位置和写入者见 md/development/core/LOOP.core.md 第 2 节。

派发后由执行者及时汇报实际会话和配置核实结果；任务完成、失败或依赖变化时，协调者更新记录，由 md/development/core/COLLABORATION.core.md 第 13.1 节确定的上级重新评估就绪任务，再派发。协调者验收时对照实际派发与结果，检查依赖、批次、并发、配置核实和归档是否相符；缺记录或矛盾须退回补查，历史遗漏如实记偏离，不能补造事前计划。

### 2.2. 持久任务状态与新会话接手

需要任务进度文件的目标，决定、当前 DAG、待办与证据位置必须记在该文件中，不依赖某个会话的记忆；不建文件的任务仍按第 0 节使用适用工作记录，不新增分类例外。新会话接手本目标时先读当前记录及适用规范，再按第 0.1 节自检后推进；核对现有结果与缺口，不从旧对话摘要推定完成或重启已结束任务。执行者把状态变化汇报给协调者，记录维护只按本节“写入者”。

## 3. 存放与写回

收尾写回上一级的 Markdown 仅包括必要证据、归纳笔记、协调者维护的对应任务进度文件；其余过程文件和临时输出不随之写回，按 md/development/core/GIT_WORKFLOW.core.md 第 2.3、6.6 节及既有证据保留要求处理。此范围不扩大删除权限。任务进度文件由协调者维护和转移，执行者只准备并交回其他收尾资料。

- 需要任务目录时，按 md/development/core/LOOP.core.md 第 7 节组织。协调者在派发时明确本目标的根 baseline、任务目录和上级任务；baseline 和根 baseline 的含义见 md/development/core/GIT_WORKFLOW.core.md 第 1.3 节。

- 新建的 任务进度文件 和 收尾笔记文件 是本地记录，不提交到 Git，不强制添加被忽略的文件。已有任务文档按本节的收尾留存规则处理；权限见 md/development/core/GIT_WORKFLOW.core.md 第 0 节。

- **归纳笔记的计数**：按协调者声明的目标计数，一个目标在根 baseline 留一份。子树结束时只交证据，不另写笔记；协调者不自己写笔记。

- **收尾时机**：全部结果合回根 baseline，或目标被明确终止时，目标收尾。只在这时写归纳笔记，在交回协调者前写好；验收需要补证据时更新同一份笔记。

- **整理记录**：已建立 任务进度文件 的目标，由协调者整理，保留五个部分、验收项及状态、最后的提交 SHA、分支名、已排除的方向及原因、下一步和待裁决事项。删去可重建的过程流水，如逐条命令输出和换行对比。

- **文件开头**：整理后的 任务进度文件 写明状态（“已结束”“已终止”或“可续接”）、最后的提交 SHA 和分支名。

- **写回位置**：整个目标收尾时，协调者复制对应任务进度文件、执行者复制其他实际应有的收尾资料到根 baseline 的 任务归档目录；已建立 任务进度文件 的目标将它与 收尾笔记文件 一起保存。baseline 上的发行与合并按开头的分类留存记录，不做自身复制。

- **逐级转移**：结果再合入上一级时，收尾记录按 md/development/core/GIT_WORKFLOW.core.md 第 6.2 节转移，直到主工作树；根 baseline 自身回收且没有接收树时的保留位置也按该节处理。

- **无源码变更或终止的目标**：无源码变更的独立验证以全部结果汇总完成作为目标收尾，不要求空 Git 合并。目标被明确终止时，写明未合入状态、已完成内容，以及未完成、未验证事项；不为留档合并未合入的结果。

- **进行中的记录**：根 baseline 不放进行中的过程文件；派生根任务的 任务进度文件 在整个目标收尾后才整理归档到根 baseline。

- **收尾留存**：新任务优先使用本文件规定的记录和既有测试记录，不另建过程文档。

- 已有过程文档按本节收尾写回范围核对，不因曾经存在而扩大转移清单。

- 已被 Git 跟踪的任务文档按正常 Git 流程处理，不自动取消跟踪。

- 收尾后只留规定记录的要求不构成删除其他文件的授权；删除仍按 md/development/core/GIT_WORKFLOW.core.md 第 6 节执行。

- **笔记内容**：写清结论、关键改动和结果、限制，以及导致失败或阻塞的超时、关键差异和最小复现信息；关键数据写进笔记，证据只写索引（提交 SHA、复现命令、输入标识），不搬完整日志或过程流水。证据文件的存放和保留例外见 md/development/core/GIT_WORKFLOW.core.md 第 2.3 节。

- 写回记录不构成清理授权；分支和工作树删除仍遵守 md/development/core/GIT_WORKFLOW.core.md 第 6 节的授权和保护条件。

## 4. 续接与优先级

本节的“目标”指协调者确定的总目标。总目标和验收标准不变、授权仍覆盖当前动作时，续用原执行者与按第 0 节适用的当前记录。同一总目标内从调研推进到获准实现等属于阶段推进；为该阶段补足实施许可不机械视为新方向，不能在许可取得前越界。改变总目标、验收标准或授权使原方向不再适用时才按新方向处理；跨写入范围前由协调者调整分工。已有派生工作树的继续沿用；从只读进入本就需要建树的阶段时，按 md/development/core/GIT_WORKFLOW.core.md 第 2.1 节创建派生树，由协调者按第 2 节建立所需任务进度文件。

只读和只写文档任务沿用原会话或指定工作记录续接；只有本就需要任务进度文件的目标才续用该文件。派发与有无 DAG 不改变第 0 节分类条件；开发和实验任务按以下规则处理：

- **继续**：总目标和验收标准不变时，在原派生工作树读当前记录接着做，或按本节的历史续接规则从历史 任务进度文件 接着做；例如会话中断换执行者、退回重改。协调者在派发中指明记录位置。

- **从历史记录接着做**：协调者在派发中指定起点是历史记录的提交还是当前 baseline。执行前确认选定提交仍可读取，再按 md/development/core/GIT_WORKFLOW.core.md 第 2.1 节创建派生树；从历史提交起步时使用该提交 SHA，并记明原因。

- **记录复制**：由协调者把历史任务进度文件 复制进新根任务派生树的任务目录，状态改为“进行中”，接着做。续接期间，baseline 中的历史副本保留不动。

- **续接时调整目标**：用户明确要求在原树续做并调整目标，或指定历史任务续做时调整目标，协调者更新“目标与验收标准”，写明改了什么、为什么改；由 md/development/core/LOOP.core.md 第 2 节规定的写入者写入。原树续做沿用原工作树、原分支和原文件。

- **新任务**：总目标或验收标准改变时，开新派生工作树和新的 任务进度文件，需要的旧结论由协调者写进派发内容；上一条规定的续接例外除外。

- **原工作树已删除**：有历史 任务进度文件 时按本节的历史续接规则处理。没有历史文件而同一未结束任务的原分支仍在时，按 md/development/core/GIT_WORKFLOW.core.md 第 2.1 节重新挂载原分支，由协调者根据执行者交回的归纳笔记、提交记录和派发内容重建记录；原分支也不存在时，按新任务处理。

- **续接收尾**：协调者更新根 baseline 同一目标目录中的任务进度文件，根任务执行者准备收尾笔记；记录都保留当前有效版本。

- 派生工作树按 md/development/core/GIT_WORKFLOW.core.md 第 2.1 节、md/development/core/GIT_WORKFLOW.core.md 第 6 节只服务一个用途并在用途结束后清理，不把旧 任务进度文件 留给下个任务。

- baseline 上的发行与合并按开头的分类用会话报告续接，收尾记录按 md/development/core/LOOP.core.md 第 3 节留存。

协调者最新的派发内容优先于记录中的“下一步”，执行者按新派发推进并汇报，协调者更新适用的任务进度文件；不建文件的任务由执行者更新会话回执或指定工作记录。方向决策与派发职责见 md/development/core/COLLABORATION.core.md 第 13.2 节；写回按 md/development/core/LOOP.core.md 第 3 节执行，提交按 md/development/core/GIT_WORKFLOW.core.md 第 3 节执行。

## 5. 多协调者

工作树选择、用途隔离和 baseline 写入范围按 md/development/core/GIT_WORKFLOW.core.md 第 2.1 节执行。任务 DAG 调度按本文件第 2.1 节执行。不同协调者不碰对方的任务记录、执行者和进程。

- 发现被占用就等待，先来先得。等待期间定期复查，例如每几分钟一次，并设置等待上限；超过上限仍被占用时上报所属协调者。

- 检查只能发现检查时可见的占用。不同协调者同时写入同一 baseline 的情况很少，出现时按下一条上报处理，不加锁。

## 7. 文档规则

本节规定默认的文档工作流；用户对本次任务的分支、文件和操作已有明确指示时，按 md/development/core/AGENTS.core.md 第 1.1 节的优先级执行。

- **说明类文档**：使用说明、操作指南、模块说明等放在 说明文档目录 下按主题组织的目录中；先查仓库 说明文档目录 下现有目录，沿用已有的同类目录，确无同类目录时再按主题新建。说明类文档只解释实现和操作；规则部分引用对应规范章节，不重新列出选择规则、路径规定或流程门禁。

- 文档和新增注释默认用中文，Markdown 使用 UTF-8、LF。

- **任务目录**：需要创建的任务文档统一放在 任务归档目录；`<任务目录>` 是 任务目录父级 下的目标目录名，命名按 项目配置中的分支或任务命名格式执行。

- 目录名示例为 任务目录命名示例。不建空目录占位，结果文件见 md/development/core/LOOP.core.md 第 7.1 节。

- 新任务的记录选择和已有任务文档的收尾见 md/development/core/LOOP.core.md 第 2 节、md/development/core/LOOP.core.md 第 3 节。仓库和源码模块的 README、长期规范及其他项目 Markdown 的维护位置按其任务分类和 md/development/core/GIT_WORKFLOW.core.md 第 7 节执行。

- 任务记录与归纳笔记的适用范围、结构、存放和维护见 md/development/core/LOOP.core.md。

- 两个例外：新建工作树时，可以按 md/development/core/GIT_WORKFLOW.core.md 第 2.2 节补齐基准提交里缺失的规范文件；收尾记录的原样转移按 md/development/core/GIT_WORKFLOW.core.md 第 6.2 节执行。这两种操作都只搬运文件，不修改内容。

- Git 正常检出或已批准的合并带来的已有文档不算主动编辑。文档发生合并冲突、又无法原样继承时，停下来报告，不用 ours/theirs、复制文件或改后缀绕过。

- 功能实际合入主干后，才在主工作树按最终结果更新相关文档。用户明确要求的纯文档维护，可以按 md/development/core/GIT_WORKFLOW.core.md 第 7 节直接在主工作树上修改；主干上的 commit 仍需要授权。

- 状态要分开说：“实验已集成，文档待主干同步”和“主干已集成，文档已同步”是两种状态。

### 7.1. 结果文件与报告

- 只写理解、复现、比较和决策需要的信息。普通报告不写绝对路径、文件哈希、机器名、生成时间、工具调用流水或完整环境快照；也不要把这些挪进另建的 metadata/manifest 文件。

- **可追溯靠 Git、CI 和测试记录。** 报告引用已有记录，必要证据写进测试报告或任务记录（记录方式见 md/development/core/LOOP.core.md），不重复抄写完整日志。正式交付本身要求的校验（依赖锁、ZIP 内容）照常执行，报告写明结果和异常。

- 不能删掉影响结论的单位、参考定义、关键参数、有效范围、失败结果和限制，也不能只展示成功的行。

- **PNG、CSV 和日志的存放**：临时输出和保留例外按 md/development/core/GIT_WORKFLOW.core.md 第 2.3 节执行；baseline 的任务目录按 md/development/core/LOOP.core.md 第 3 节处理。

- CSV：一行一个对象；列名带单位；缺失值留空并给出状态，不用 0 或旧值顶替；统计用未舍入的值。

- JSON：只在程序要读取、保存配置或交换数据时生成；必须能直接解析，不用 `NaN`、注释或尾随逗号。

- Markdown：段落内不手动换行；修订时直接替换冲突内容，不追加“补充说明”；不适用的章节直接省略，不写“无”“不适用”。

### 14.1. 裁决、通知与独立授权

- L0–L1：协调者在任务范围内自主决定。
- L2：协调者在任务范围内自主决定，事后通知用户；在“已自主决定（L2）”中逐项写决定与理由。破坏性 API/SPI 变更和第三方依赖变化按实际影响判级，命中 L2 时适用本项，不再单设这两类变更的用户授权门禁；若实际影响达到 L3 则适用下一项。
- L3：先交用户裁决，给事实、影响、可选方案与建议，未获决定前只暂停依赖部分。已有明确且仍有效的用户指令覆盖该方向时直接执行，不重复确认。

仍需用户授权的独立门禁有五类，不因 L0–L2 的自主决定或免确认模式而跳过：主干提交与合并；push、tag、release、创建 PR、删除远端分支；目录与工作树删除；SDK 边界变更；修改现行规范。目录与工作树删除需用户授权；满足 md/development/core/GIT_WORKFLOW.core.md 第 6 节删除条件的，视为已获默认授权。删除条件与执行分工只在该节定义；派发注明依据的条件条款与精确路径，不扩大删除范围。其他 Git 操作细节见 md/development/core/GIT_WORKFLOW.core.md 第 0、5 节，SDK 具体边界及落实见项目交付规范。

现行规范是正在作为会话工作规则生效的规范，包含任何工作树实际加载生效的规范文件，具体路径由项目列明；修改必须先获用户明确批准，包括小改、单行修改与紧急修正，协调者 L0–L2 自主决定不涵盖此项。候选规范是用户指定用于研究、比较和修订，尚未替换成现行工作规则的材料；按用户指示修订候选不受这项现行规范门禁限制。读取候选作解释不会使其自动成为现行规范，Git 跟踪、忽略状态或文件名也不能代替该属性判断。

核心状态机变更按风险表定级。独立授权、任务既定范围和风险裁决分别核对，协调者自主决定不产生额外操作许可。

先完成必要调研再提交 L3 裁决或请求独立授权。事实问题中能自行取得的信息由协调者在动作边界内调研或派执行者调研；确实只能由用户提供的必要输入，调研后可由协调者向用户提问，在回复的“待办与风险”中标明“需要你提供”，说明缺什么、影响和下一步。这是取得事实输入，不是把决定交给用户；不虚构输入，只暂停依赖该输入的部分，继续其他可独立推进的工作。

执行者和子代理不直接向用户提问；分别按 md/development/core/COLLABORATION.core.md 第 13.3、13.4 节向上报告需要协调者裁决的事项。
